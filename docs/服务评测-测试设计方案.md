# 服务评测测试设计方案 v2（WWW 2027 Industry Track）

> v2 重写说明：v1 假设服务评测由本地平台调度。训练战役期间本地依赖被证明是
> 单点（Mac 休眠、监控线程崩溃、SSH 风暴导致队列三次停摆），现已整体重构为
> **远端执行器架构**——调度循环常驻 GPU 服务器。本方案按新架构编写，
> 执行机制均为已在训练战役中实测过的做法。

## 0. 现状与架构

### 训练战役的实际运行方式（已验证）

调度器（`scripts/campaign_runner.py`，已入库）常驻 GPU 服务器
（`/home/T0ng/campaign_runner.py`），独立完成：队列（8 槽位）、选卡
（空闲显存最大 + 在途预留扣减）、tmux 启动、退出码收割、metrics.py 出分、
结果表追加（`campaign_results.csv`）、lightgaussian 依赖链。本地 Mac 只做
定期收割，断联/休眠不影响任何流程。

### 训练战役实况（2026-10-11）

- 矩阵 9 场景 × 20 算法：**全部场景达到 20/20**（stump 的 lightgaussian 为最后一个在途项）。
- 结果表 `campaign_results.csv`：145+ 行（PSNR/SSIM/LPIPS/PLY 体积）。
- 事故与修复记录：GPU 队列持久化签名 bug、tmux 清理误杀、COLMAP OpenGL 崩溃
  （改 CPU SIFT 绕过）、内存盘 95% 危机（已完成任务产物定向清理）——全部闭环。

### 服务评测的运行方式（本方案）

沿用同一执行器模型：在 `campaign_runner.py` 中新增 **export** 与 **simulate**
两个阶段函数，服务评测的导出与模拟同样常驻服务器自动推进；仅 L3 浏览器真跑
需要本机浏览器。本地平台队列保持禁用，只作观察窗口。

## 1. 被测对象

- 训练矩阵产出的 9 场景 × 20 算法标准 SH PLY（30k 迭代版本）。
- 表示统一规则：锚点类（scaffold-gs、octree-gs）先经
  `export_scaffold_gaussians.py` 解码为标准高斯（已验证：drjohnson 解码
  106.9 万高斯点并成功切出基础层+25 块）；其余算法直接切片。

## 2. 四层测试

| 层 | 内容 | 在哪跑 | 产出 |
|---|---|---|---|

| L2 调度模拟 | 六策略 × 4 网络档全矩阵 | 服务器执行器 simulate 阶段（8 进程并行） | 模拟主表 CSV（创新参数主数据） |

| L4 证据汇总 | 全量收割 + 聚合脚本生成论文表格 | 本机 | T1–T3 表、F1–F3 图数据 |

## 3. 指标定义（论文口径，一处定义、处处使用）

| 指标 | 定义 | 来源 |
|---|---|---|
| TTFR | 基础层下载+排序+首次渲染完成的时刻 | 模拟器 `ttfr_ms`；浏览器实测 `ttfrMs` |
| t50/t90 画质时刻 | 视觉增益累计达全场景 50%/90% 的时刻 | 模拟器 `t50_view_ms` / `t90_view_ms` |
| 传输字节 | 对应画质节点时的累计下载字节 | 模拟器逐块累加；浏览器 `totalBytes` |
| P95 帧时间 | 最近 240 帧时长的 95 分位 | 浏览器 HUD/遥测 |
| 客户端档位 | 台式独显 / 集显笔记本 / 中端安卓（点数上限 3M/1.2M/0.5M，目标帧率 60/45/30） | `profile=` 参数 + 运行时自适应 |
| 自适应事件 | 运行中点数上限上调/下调次数 | 上报字段 `adapt_up` / `adapt_down` |
| 失败阶段 | manifest / webgl / worker / chunks / internal | 上报字段 `fail_stage` |

## 4. 变量控制

- **自变量**：传输策略（naive/bandwidth/viewport/gpu/joint/full）、网络档
  （2Mbps/120ms、10/60、30/30、100/10）、客户端档（仅 L3）。
- **控制变量**：模拟全部在同一服务器；浏览器统一 Chrome、基准模式
  `cache:"reload"` 绕缓存；模型均为 30k 迭代；同一场景组的对比使用同一份切片资产。
- **如实说明**：L3 在 localhost 跑，网络近似无限——它验证渲染侧真实行为
  （解码、上传、排序、首帧），网络维度由 L2 覆盖。论文中两者分开陈述。

## 5. 测试矩阵规模

### L2 模拟矩阵（全量）
180 模型 × 6 策略 × 4 网络档 = **4320 行**。单次模拟 2–5 秒，服务器 8 进程
并行约 **3–6 小时**。资产分批（批 20 模型，约 20GB），跑完即删（资产可由
PLY 重新导出，CSV 与清单留存本地）。

### L3 浏览器真跑（抽样验证）
每场景 5 个代表模型（vanilla、最强压缩、scaffold 解码、体积最小、体积最大）
× 4 策略（joint、full、naive、bandwidth）× 3 客户端档 = **540 行**。
单行 12–20 秒，约 **2–3 小时**，支持断点续跑（按行记录已完成组合）。

## 7. 数据产出物

1. **T1 主对比表**：策略 × 网络档 → 平均 TTFR、t90 字节、t90 时刻（L2 聚合）。
2. **T2 场景规模表**：三个规模桶内复现策略排序。
3. **T3 客户端表**：三档画像的 TTFR/帧率/P95/自适应事件（L3）。
4. **F1 TTFR 累计分布曲线**（六策略，同场景组）。
5. **F2 字节-画质曲线**（六策略）。

## 9. 验收标准

1. L1：180/180 导出成功且清单校验通过；失败模型记录原因并列入限制。
2. L2：模拟行数 ≥ 4300，缺行 < 1%；≥ 7 个场景上"joint 的 t90 字节 < full 全量字节"。
3. L3：540 行全部有效；三档画像帧率/P95 呈阶梯差异；自适应事件计数 > 0。
4. 一致性：L3 策略排序与 L2 方向一致（不一致以 L3 为准并分析）。
5. 全部数据落本地磁盘；T1–T3、F1–F3 由脚本从 CSV 生成。

## 10. 风险与如实限制（含战役实测教训）

| 风险/教训 | 应对 |
|---|---|
| 本地依赖是单点（训练战役三次停摆的根因） | 已重构：调度常驻服务器；L3 是唯一本机环节，有续跑 |
| 监控/记账线程会僵死 | 执行器状态以服务器侧退出码为准；看门狗对账脚本兜底 |
| tmux 会话清理曾误杀在跑任务 | 清理脚本跳过 campaign- 与 wgsc- 会话；清理仅在跑批间隙执行 |
| COLMAP 的 OpenGL 上下文在无显示环境崩溃 | 纯 CPU SIFT（`--SiftExtraction.use_gpu 0` 等参数）已验证 |
| 内存盘写满（曾达 95%） | 分批导出+即用即删；每小时水位检查；指标文件即时收割本地 |
| 解码类模型（scaffold/octree）体积膨胀 | 对比分"原生紧凑表示"与"解码表示"两组，注明网页端需显式高斯 |
| 解码仅保留 DC 颜色 | 质量指标以各算法原生评测为准；服务层对比注明近似 |
| 本机休眠中断 L3 | caffeinate 24h + 断点续跑 |
| 浏览器抽样可能漏极端模型 | L2 全量兜底；抽样含每场景体积最小/最大两个极端 |
