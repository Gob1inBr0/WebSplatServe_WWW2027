# 服务评测测试设计方案（WWW 2027 Industry Track）

> 目标：训练战役（180 个模型）收尾后，用一套固定的流程产出论文服务层的全部创新证据。
> 本方案回答四个问题：测什么、怎么测、测多少、产出什么。

## 1. 被测对象与前提

- **被测模型**：训练战役产出的 9 场景 × 20 算法 = 180 个标准 SH PLY。
- **前提条件**：训练战役 180/180 完成（当前 ~159，kitchen 的 COLMAP 与 lightgaussian 压轴波进行中）。
- **表示统一规则**：所有模型先变成标准 SH PLY 再切片。锚点类（scaffold-gs、octree-gs）先经 `export_scaffold_gaussians.py` 解码；解码类模型记录解码后体积。

## 2. 测试层次（四层）

| 层 | 内容 | 在哪跑 | 产出 |
|---|---|---|---|
| L1 导出验证 | 每个模型切成"基础层+增量块"，校验清单 | 服务器（执行器扩展） | 180 份渐进资产 + 导出清单 |
| L2 调度模拟 | 六策略 × 网络档全矩阵模拟 | 服务器（纯 CPU） | 模拟主表 CSV（创新参数主数据） |
| L3 浏览器真跑 | 真渲染 TTFR/帧率/P95 + 客户端画像 | 本机 Chrome | 真跑子集 CSV（对 L2 的实证校验） |
| L4 证据汇总 | 遥测 + 全量收割 + 论文表格生成 | 本机 | 论文表格与图表数据 |

## 3. 指标定义（论文口径，一处定义、处处使用）

| 指标 | 定义 | 来源 |
|---|---|---|
| TTFR | 基础层下载+排序+首次渲染完成的时刻 | 模拟器 `ttfr_ms`；浏览器实测 `ttfrMs` |
| t50/t90 画质时刻 | 视觉增益累计达全场景 50%/90% 的时刻 | 模拟器 `t50_view_ms` / `t90_view_ms` |
| 传输字节 | 达到对应画质节点时的累计下载字节 | 模拟器逐块累加；浏览器 `totalBytes` |
| P95 帧时间 | 最近 240 帧时长的 95 分位 | 浏览器 HUD/遥测 |
| 客户端档位 | 台式独显 / 集显笔记本 / 中端安卓三档的点数上限与目标帧率 | `profile=` 参数与运行时自适应 |
| 自适应事件 | 运行中点数上限上调/下调的次数 | 上报字段 `adapt_up` / `adapt_down` |
| 失败阶段 | manifest / webgl / worker / chunks / internal 固定枚举 | 上报字段 `fail_stage` |

## 4. 变量控制

- **自变量**：传输策略（6 种）、网络档（4 档：2Mbps/120ms、10/60、30/30、100/10）、客户端档（3 档，仅 L3）。
- **控制变量**：同一服务器跑全部模拟；浏览器统一 Chrome + 关闭其他标签；基准模式 `cache:"reload"` 绕过缓存；模型均为 30k 迭代版本。
- **如实说明**：L3 在本机 localhost 跑，网络近似无限——它验证的是**渲染侧**真实行为（解码、上传、排序、首帧），网络维度由 L2 覆盖。两者结合才是完整证据链，论文里分开陈述。

## 5. 测试矩阵规模

### L2 模拟矩阵（全量）
180 模型 × 6 策略 × 4 网络档 = **4320 行**。单次模拟 2–5 秒，服务器并行 8 进程，预计 **3–6 小时**。挂到远端执行器，断联不影响。

### L3 浏览器真跑（抽样验证）
抽样原则：每个场景选 5 个代表模型（vanilla、最强压缩、scaffold 解码、一个剪枝类、一个量化类），× 4 策略（joint、full、naive、bandwidth）× 3 客户端档 = **9 × 5 × 12 = 540 行**。
单行 12–20 秒，预计 **2–3 小时**。需要本机不休眠（caffeinate 拉长到 24h）。

### 导出体积策略
渐进资产与模型同量级，内存盘放不下 180 份全量资产（当前已用 233GB/315GB）。**分批导出→跑完 L2→删除资产→下一批**，每批 20 个模型（约 20GB）。PLY 本体保留（可重新导出）。

## 6. 论文主张 → 测试映射（每条主张都有对应数据）

| 主张 | 验证测试 | 数据位置 |
|---|---|---|
| 基础层先行让首帧大幅提前 | L2：joint 的 TTFR vs full 的完整下载时间 | L2 主表 |
| 自适应策略以更少字节达到目标画质 | L2：t90 时刻的字节 vs full 全量字节 | L2 主表 |
| 多信号联合优于单信号 | L2：joint vs bandwidth/viewport/gpu/naive 排序 | L2 主表 |
| 场景规模不影响结论 | L2 按场景规模分桶（<1M/1M–5M/>5M）复现排序 | L2 分桶表 |
| 客户端画像自适应有效 | L3：三档画像的帧率/P95 对比 + `adapt_up/down` 事件计数 | L3 子集表 + 遥测 |
| 模拟结论在真实浏览器成立 | L2 与 L3 的 TTFR/字节方向一致性 | 对照表 |

## 7. 数据产出物（论文可直接引用）

1. **T1 主对比表**：策略 × 网络档 → 平均 TTFR、t90 字节、t90 时刻（L2 聚合）。
2. **T2 场景规模表**：三个规模桶内复现策略排序。
3. **T3 客户端表**：三档画像的 TTFR/帧率/P95/自适应事件（L3）。
4. **F1 TTFR 累计分布曲线**（六策略，同一场景组）。
5. **F2 字节-画质曲线**（达到 x% 画质所需字节，六策略）。
6. **F3 逐块到达时间线**（调度器 `write_trace_csv` 输出，选 2 个代表场景）。
7. **部署证据**：`campaign_results.csv`（训练对比）+ 遥测汇总（真实访问的服务指标）。

## 8. 执行计划

| 阶段 | 内容 | 预计耗时 | 依赖 |
|---|---|---|---|
| P0 | 训练 180/180 收尾确认 | 进行中（kitchen + lightgaussian 压轴） | — |
| P1 | L1 导出战役（分批，执行器扩展 export 步骤） | 3–5 小时 | P0 |
| P2 | L2 模拟矩阵（执行器并行 8 进程） | 3–6 小时 | P1 |
| P3 | L3 浏览器真跑（本机 Chrome + caffeinate 24h） | 2–3 小时 | P1（与 P2 可并行） |
| P4 | L4 汇总：收割 + 聚合脚本生成 T1–T3、F1–F3 | 1 小时 | P2、P3 |

聚合脚本新增 `web/tools/summarize_serving_campaign.py`：输入 L2/L3 的 CSV，输出上述表格（markdown + CSV 双格式），数字不经手工抄写。

## 9. 验收标准

1. L1：180/180 导出成功，每份清单通过校验（块划分闭合、基础层在前、contentHash 存在）；导出失败模型记录原因（非 SH、解码失败等）并列入限制。
2. L2：模拟行数 ≥ 4300，缺行 < 1%；六策略在 ≥ 7 个场景上呈现"joint 的 t90 字节 < full 全量字节"。
3. L3：540 行全部有效；三档画像的帧率/P95 呈现阶梯差异；自适应事件计数 > 0。
4. 一致性：L3 的策略排序与 L2 方向一致（不一致时以 L3 为准并分析原因）。
5. 全部数据落本地磁盘（内存盘只作中转），T1–T3 由脚本从 CSV 生成。

## 10. 风险与如实限制

| 风险 | 应对 |
|---|---|
| 部分算法模型无法导出（非 SH、产物损坏） | 记录原因清单，论文标注"n/20 算法参与服务对比" |
| 解码类模型（scaffold/octree）体积膨胀 | 对比表分"原生紧凑表示"与"解码表示"两组呈现，注明网页端需要显式高斯 |
| 解码仅保留 DC 颜色 | 质量指标以各算法原生评测为准；服务层对比注明近似 |
| 本机休眠中断 L3 | caffeinate 24h；L3 支持断点续跑（按行记录已完成的组合） |
| 内存盘重启丢失 | 结果 CSV 每小时收割本地；资产为派生物可由 PLY 重新导出 |
| 浏览器采样可能漏掉极端模型 | L2 全量覆盖兜底；抽样模型选取时包含每场景体积最小/最大两个极端 |

## 11. 与现有资产的复用关系

- 导出：`web/tools/export_websplatserve_assets.py`（已验证：drjohnson scaffold 解码模型切出基础层+25 块）。
- 模拟：`web/serving/adaptive_scheduler.py`（`simulate_manifest` + `write_trace_csv`，14 个测试模块覆盖）。
- 浏览器：`web/viewers/benchmark.html`（六策略矩阵、客户端画像、遥测上报均已实测）。
- 执行器：`campaign_runner.py` 增加 export/simulate 两个阶段函数，复用现有队列与选卡逻辑。
